---
title: Replay Graph And Clusters
description: Use replay graph for semantic triage within one artifact root and replay cluster for repeated failure shapes across runs.
---

`replay graph` and `replay cluster` are the replay commands you reach for after `replay summarize`, `replay timeline`, or `replay capsule` stop being enough.

- Use `replay capsule` when one artifact root failed and you want the shortest operator path to the primary failure.
- Use `replay graph` when you need a stable semantic model over one artifact root: failures, actions, selectors, telemetry, artifacts, and generated scenario-draft provenance.
- Use `replay cluster` when the question is no longer "what failed here" but "is this the same failure pattern as the last runs?"

## Commands

```bash
luotsi replay graph --artifacts ./artifacts/my-run --write-json --write-markdown
luotsi replay graph --artifacts ./artifacts/my-run --failed --node-kind failure --write-markdown
luotsi replay graph --artifacts ./artifacts/my-run --node-kind selector --write-markdown
luotsi replay graph --artifacts ./artifacts/my-run --action waitVisible --limit 50
luotsi replay graph --artifacts ./artifacts/my-run --selector "Sign in" --limit 50
luotsi replay cluster --artifacts ./artifacts/ci-runs --write-json --write-markdown
```

## Replay graph contract

`luotsi replay graph` emits `luotsi-replay-graph.v1`, a stable node-and-edge view over replay artifacts.

The top-level fields that matter most are:

| Field | Meaning |
|---|---|
| `schema` | Always `luotsi-replay-graph.v1` |
| `artifact_root` | Root directory the graph was built from |
| `query` | Applied filters: failure-only, node kind, edge kind, action, selector, and limit |
| `node_count`, `edge_count` | Returned graph size after filtering |
| `total_node_count`, `total_edge_count` | Full graph size before filters |
| `matched_node_count`, `matched_edge_count` | Query match size before `--limit` is applied |
| `truncated` | `true` when `--limit` capped the matched result |
| `node_kinds`, `edge_kinds` | Counts for the returned graph view |
| `insights` | Agent-readable highlights about failures, selectors, telemetry, and draft provenance |
| `actions` | Suggested next commands for opening, scrubbing, or narrowing the graph |
| `nodes`, `edges` | Stable graph payload |

Filtering returns a focused subgraph with one-hop context, so the result stays useful instead of becoming a full replay dump.

## Node kinds

The graph promotes raw replay evidence into stable node kinds:

| Kind | Meaning |
|---|---|
| `session` | One `session-replay.json` session |
| `event` | One normalized timeline event from `session-timeline.jsonl` |
| `failure` | Failure-relevant timeline event or terminal failure |
| `failure_capsule` | `failure-capsule.json` summary node |
| `scenario` | Scenario entry from a failure capsule |
| `artifact` | Screenshot, logcat, hierarchy, report, or metadata file linked to a scenario |
| `action` | Promoted action such as `waitVisible`, `tap_text`, or `take_screenshot` |
| `selector` | Promoted selector, currently text-based |
| `screen_state` | Screen or screenshot observation |
| `telemetry_signal` | Semantic telemetry signal emitted by the app or observed by Luotsi |
| `scenario_draft` | Generated scenario draft summary |
| `generated_step` | Step generated by `replay scenario-draft` |
| `draft_source` | Source family for generated steps, such as inspect command or telemetry |
| `draft_normalization` | Cleanup or normalization applied while generating a draft |

## Edge kinds

Edges describe how those promoted nodes relate to one another:

| Kind | Meaning |
|---|---|
| `next` | Timeline ordering within one source timeline file |
| `indicates` | Event points to a failure node |
| `has_capsule` | Session has a failure capsule |
| `contains` | Capsule contains a scenario |
| `has_artifact` | Scenario links to an artifact |
| `describes_action` | Event describes an action node |
| `mentions_selector` | Event mentions a selector node |
| `observes_screen` | Event observes a screen or screenshot state |
| `observes_telemetry` | Event observes a semantic telemetry signal |
| `generates_step` | Scenario draft generates a step |
| `derived_from` | Generated step came from a source event family |
| `uses_source` | Scenario draft uses a source family |
| `applies_normalization` | Scenario draft applied a normalization |

## Useful graph queries

These are the practical queries that usually answer the next question fastest:

- `--failed` when you want only failure-relevant nodes and their local context
- `--node-kind selector` when the question is which text selectors or labels are actually present in the replay evidence
- `--node-kind generated_step` when you are auditing `replay scenario-draft` output back to its origins
- `--action <text>` when you want to follow a particular wait or interaction across the replay evidence
- `--selector <text>` when you want one label or control name narrowed across events, actions, and failures

## Replay cluster contract

`luotsi replay cluster` groups failed replay sessions by normalized failure shape.

That makes it the right command when:

- a CI directory contains multiple failing artifact roots
- you need grouped failure shapes instead of one-run detail
- you want the latest matching bundle plus the next replay/search commands for that cluster

Use it as a triage reducer, not as a replacement for `replay capsule` or `replay graph`. In practice the flow is:

1. Run `replay cluster` on a directory of replayable artifact roots.
2. Pick the cluster that matches the failure class you care about.
3. Follow the suggested replay commands into `replay capsule`, `replay graph`, `replay scrub`, or `replay search` for the latest matching bundle.

## Practical triage loop

```bash
luotsi replay capsule --artifacts ./artifacts/failing-run --write-readme --write-json
luotsi replay graph --artifacts ./artifacts/failing-run --failed --write-markdown
luotsi replay graph --artifacts ./artifacts/failing-run --node-kind selector --write-markdown
luotsi replay cluster --artifacts ./artifacts/ci-runs --write-markdown
```

Use `replay graph` when you are still reasoning within one bundle. Use `replay cluster` when you are deciding whether the current failure belongs to a larger recurring class.
